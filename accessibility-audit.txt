Issue: telerik/xaml-docs#3249
Audit date: 2026-10-27
Source baseline: 40bab103ec094afb91f91a1dfa340cc4bbc8ea56

# Executive Summary

The documentation has established organization, descriptive prose around many
examples, and reusable authoring conventions, but accessibility practices are
inconsistent. The main risks are filename-based image alternatives, generic
links, discontinuous heading outlines, tables without meaningful header
relationships, and instructions that require interpretation of screenshots.
Estimated authoring maturity: developing, not consistently enforced. This is
a qualitative assessment, not a repository-wide numerical score.

This audit evaluates ONLY Markdown documentation, authoring practices, and
referenced documentation assets. It does NOT evaluate Telerik WPF features,
runtime behavior, product keyboard or screen-reader support, report/viewer/
designer accessibility, generated reports, or the accuracy of product
accessibility claims. References to such topics identify documentation only.

There are 26 grouped findings below: 18 Medium and 8 Low. No Critical or High
barrier was established at this source-only level of assurance. Medium issues
still warrant a scheduled remediation backlog, especially on entry-point
articles and shared templates. A finding groups one authoring problem and may
cover several occurrences; it is not a count of every affected source line.

Other asset findings concern the embedding source and surrounding prose,

Census method: enumerate tracked .md paths with git ls-files; exclude the ten
files above; decode UTF-8; remove initial YAML front matter; track matching
backtick/tilde fences, including indented fences; inspect only prose outside
fences. Count ATX headings, inline Markdown images/links, and HTML image/media
declarations. Filename matches compare lowercased alphanumeric image labels
with the target filename stem. The generic-link allowlist is: here, click
here, click here for more, learn more, read more, more, this article, this link,
and link. Opening fences with no information string are counted, not closing
fences. Findings were then checked manually with surrounding source context.

These are heuristic candidate counts, not Markdown-parser or WCAG verdicts.
Reference-style syntax, multiline HTML, includes, and external snippet bodies
are not exhaustively represented. Conditional branches were not expanded in
the census; confirmed examples below identify WPF-visible or unconditional
source. Counts are reproducible only against the stated baseline and method.

No rendered documentation build, assistive-technology session, external video
inspection, or contrast measurement was performed. Heading landmarks supplied
by the site shell, final table semantics, iframe accessible names, captions,
audio description, custom article-card behavior, and motion controls require
rendered-page follow-up. This report is not WCAG conformance certification.
The checked-in configuration does not provide a Markdown accessibility test
command; no new dependencies, test framework, or publishing changes are needed
for this report-only deliverable.

Severity interpretation:
  Critical — demonstrated widespread barrier preventing content understanding.
  High — demonstrated substantial documentation-access barrier needing urgent repair.
  Medium — confirmed authoring issue reducing usability or equivalent access.
  Low — limited-impact clarity or consistency improvement.
Potential rendered failures are qualified rather than assigned an invented
Critical/High rating. Skill scores and issue severity are separate measures.

Source-census results (occurrences / distinct article files):
  ATX heading jumps:                         1,087 / 667
  No source H1:                                423 / 423
  Multiple source H1s:                          13 / 13
  Generic inline link labels:                  751 / 473

    of these, no alt attribute:                  23 / 23

Denominators for the counted inline syntax: 5,217 Markdown image references,
17,597 Markdown links, and 1,921 fenced blocks. The census also found 310 pipe
table separator lines; this is not a full table inventory because HTML tables
and included tables also occur. Categories overlap and must not be summed
into an affected-page total or a conformance percentage.

Most frequent candidates are heading discontinuities, filename-derived image
labels, and generic links. Their prevalence supports a systematic authoring
response rather than fixing only the example articles.

Important qualifications and counterexamples:
- Of the 423 files without a source H1, 422 are knowledge-base articles; the
  other is F26. Establish title-injection behavior before bulk remediation.
- Conditional Silverlight content was included in raw scan counts, but is not
  used to infer a WPF rendered-page failure.
- Empty labels appear in TabbedWindow, migration, and a demos troubleshooting
  article. In the migration article, Properties/Target framework steps already
  state the required choices. Empty alt may intentionally suppress redundant
  screenshots; it is not automatically an accessibility defect.
- The palette table supplies hexadecimal values. Similarly,
  /home/runner/work/xaml-docs/xaml-docs/controls/radchart/features/layout-mode.md:68–84
  mentions red rectangles but follows with textual descriptions of differences.
  This supports clearer wording, not a confirmed color-only barrier.
- /home/runner/work/xaml-docs/xaml-docs/testing/appium/getting-started.md:154–158
  mentions flashing blue AND an "Active" to "XPath Ready" text-status change.
  Do not remove useful status text or classify this as color-only instruction.
- "Click the empty square that's on the right" at
  /home/runner/work/xaml-docs/xaml-docs/controls/radtreeview/populating-with-data/item-template.md:43–49
  has Source-property and DataBinding context. Prefer the property/menu name,
  but direction words alone do not prove inaccessible instructions.
- The Appium article has a 51-line code sample at lines 29–81 with an
  introduction and comments. The rubric has no hard maximum sample length.
  Length alone is not a finding; split only where it improves comprehension.
- No confirmed dependence on syntax highlighting alone was found in the manual
  sample. Lack of a language tag is a separate, demonstrated issue.
- A URL can be essential literal data, such as a service endpoint. Do not
  automatically replace every bare URL; use descriptive links for navigation
  and preserve literal configuration values in code.

Bulk-remediation candidates: reviewed generic links, figure captions misused
as headings, language tags where the language is unambiguous, and shared layout
tables. Image descriptions, meaningful blank-cell replacements, acronyms, and
screenshot equivalence require human judgment. Repair includes once and preview
their consumers. Do not automatically rewrite product terminology or code.

# Authoring Guideline Improvements

Suggested additions to the contributor guidance and wiki, not product guidance:

1. Require one meaningful page title and a sequential outline. Document exactly
   when a renderer supplies H1. Use captions, not heading levels, for figures.
2. Require text-complete procedures. Name the control/menu/property and value;
   never require a reader to locate an unlabeled colored or positioned item.
3. Explain informative image purpose/results. For complex diagrams, provide a
   nearby extended description. Document when empty alt marks a redundant or
   decorative image. Avoid repeating a complete caption word for word.
4. Require destination-specific links; review a links-only list. Keep labels
   for the same destination consistent where their purpose is the same.
5. Use real column/row headers for data, lists for layout, meaningful values for
   absence, and a lead-in explaining complex comparisons. Split grouped tables.
6. Introduce each logical code example with purpose, location, prerequisites,
   substitutions, and relevant outcome. Tag fences, retain shared introductions
   for C#/VB alternatives, and provide context for external snippets.
7. Expand unfamiliar acronyms on first use, prefer imperative short steps, and
   split long notices. A reading-grade target is guidance, not a way to rewrite
   identifiers or discard necessary technical terminology.
8. Standardize >note, >tip, >important, and >warning. Require complete,
   self-contained content and a type appropriate to the notice's consequence.
9. Give embedded frames descriptive titles and adjacent alternative routes.
   Document caption/transcript review and avoid persistent uncontrolled motion.
10. Require a PR reviewer to check outline, links, images, tables, code context,
    and media alternatives. Preview through the actual documentation renderer.
    Record narrowly scoped exceptions with reasons and review dates.

# Automation Opportunities

These are proposed controls, not tooling installed or workflows changed by
this audit. Use the existing documentation pipeline when implementing them.

Source checks suitable for Markdown linting:
- Heading increment and single-title rules (for example markdownlint MD001,
  MD025, MD041), with explicit KB/title-template exceptions.
- Fence language rules (MD040), accepting existing C#, VB.NET, XAML, json,
  powershell, and text conventions rather than forcing language renames.
- Empty image labels (MD045) as review candidates, not an unconditional ban on
  decorative images. Inspect HTML <img> attributes separately.
- An approved parser-based link-text check; compare identical labels with
  different targets within a rendered article and flag navigation bare URLs.
  Account for fragments, conditional branches, and Liquid slug expressions.

Documentation validation and editorial checks:
- Require headers on real data tables; flag empty header/data cells and layout
  tables for review. Avoid false positives on escaped pipes in code.
- Warn on alt text matching filenames; require human confirmation of equivalent
  information. Automation cannot author trustworthy screenshot descriptions.
- Check iframe title presence, media alternative links, local asset existence,
  and animated-asset metadata; test actual playback controls in rendered output.
- Warn on unusually long prose sentences, inconsistent placeholders, untyped
  callouts, and code blocks without nearby explanations. Keep these advisory:
  adjacent language tabs and includes may share one introduction.

CI/CD and repository policy:
- Start with changed .md files AND their included templates/assets; expand
  includes and WPF Liquid branches before rendered checks.
- Run source checks for pull requests and repository-dispatch-created articles.
  Report file, line, rule, and a suggested fix; do not silently rewrite content.
- Preserve a legacy baseline and require an explanation for exceptions; ratchet
  down debt by section instead of blocking every contribution on all 3,328 files.
- Add a periodic documentation-only rendered audit for headings, table headers,
  named frames, custom components, keyboard reading, and media alternatives.
  Use browser accessibility validation as a supplement to human review.

## Article scoring interpretation

The companion JSON scores three manually reviewed examples, not all articles.
Each object follows the required skill's eight-dimension format and computes
sum(score × weight), rounded to one decimal. A dimension with no applicable
source construct receives 5 with an explicit rationale; this does not certify
rendered output. This convention can increase a short article's score, so scores
must be read alongside findings and must not be averaged into a repository score.
External snippet bodies and custom card rendering were not scored. The finding
catalog is broader than this deliberately small illustrative scoring sample.
